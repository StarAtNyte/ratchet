# ldmatrix_wideK_conflict_free_face (16-bit operand faces with wide K: a bank-conflict-free `ldmatrix` face with zero extra smem)

> One file per hardware interface. Operator-agnostic; mechanism only.
> Related entries: [`warp_mma_f16`](warp_mma_f16.md) §3 (the `ldmatrix` trio feeding `mma.sync`; this entry
> is its **face**), [`ldmatrix_stmatrix`](ldmatrix_stmatrix.md) gotcha 8 (the 8×8 tile face, another
> conflict-free face), [`cp_async`](cp_async.md) (per-thread 16 B copies on the write side),
> [`wgmma_ss_min_gemm`](wgmma_ss_min_gemm.md) §2 (construction of the same swizzle atom),
> [`smem_traffic_triage`](smem_traffic_triage.md) (triage first: this entry only treats the **conflict
> type**).

## Purpose

Give a **K-contiguous 16-bit operand face** (`(M, K)`, K the contiguous mode) that is fed in by `cp.async`
and read out by warp-level `ldmatrix` an smem layout in which **every phase of every `ldmatrix` is free of
bank conflicts**, **without using a single extra byte of smem**: store the face as several 128 B swizzle
(`K_SW128`) boxes; the write side still goes through `partition_D`, the read side still through
`make_tiled_copy_A/B` + `partition_S`; the code on both sides is **the same** as for a flat face — only the
construction of the layout and the way views are taken change.

Cost of not using it: on a flat face with K = 64 / 128 / 256 16-bit elements (row pitch 128 / 256 / 512 B,
all integer multiples of 128 B), **every** 8×8 phase of **every** `ldmatrix` is an **8-way conflict** — one
operand fetch takes 8 wavefronts instead of 1. In NCU it looks like this: `bankconf_ld` one to two orders of
magnitude above the healthy value for the same size, `stall_mio` / `short_scoreboard` dominant,
`mio_throttle` the bulk of stalls, `tensor%` collapsed to single digits, while DRAM bytes / grid / block /
registers are all normal. The values are **all correct** — this deviation is completely invisible to
correctness.

## When needed (trigger)

- The operand face is a flat K-contiguous face such as `cute.make_layout((M, K), stride=(K, 1))`, and
  `K × 2 B` is an **integer multiple of 128 B** (16-bit K = 64, 128, 192, 256 …); the read side is
  `ldmatrix` (whichever `transpose` member, see gotcha 4);
- NCU: `bankconf_ld` ≫ the healthy line for the same size, `smem_wavefronts_ld` over the line along with it
  (conflict type, triaged per [`smem_traffic_triage`](smem_traffic_triage.md); the volume type does not
  belong to this entry); `LDSM` present in the per-opcode ledger; `mio_throttle` + `short_scoreboard` over
  half of the stall ledger;
- You want to fit the face into a fixed smem budget (padding to an odd multiple of 16 B row pitch is the
  other route, at 6–12% more smem, see gotcha 3).

## Mechanism: why a face with a row pitch that is an integer multiple of 128 B is necessarily 8-way conflicting for `ldmatrix`

smem is 32 banks × 4 B, and one wavefront serves non-overlapping banks within 128 B. One 8×8 phase of
`ldmatrix` has 8 lanes each give one row address, each row fetching **16 B** (8 16-bit elements). Cut smem
into 16 B chunks with chunk number `q = byte address / 16`; the 8 chunks within one wavefront are
conflict-free ⇔ the `q mod 8` are pairwise distinct.

For a flat face with row pitch P bytes, chunk c of row i has `q = i·(P/16) + c`:

| Row pitch P | P/16 | `q mod 8` (i = 0..7) | Conflict |
|---|---|---|---|
| 128 / 256 / 512 B (K = 64 / 128 / 256) | 8 / 16 / 32 | all the same | **8-way** |
| 144 B (K = 64 + 8 pad) | 9 (odd) | 8 distinct | none (cost +12.5% smem) |
| 272 B (K = 128 + 8 pad) | 17 (odd) | 8 distinct | none (cost +6.25% smem) |
| 128 B + `K_SW128` swizzle | 8, but the chunk number is `⊕ (i mod 8)` | 8 distinct | **none, zero extra smem** |

`K_SW128` is "the column number `c` of the 16 B chunk (3 bits) XOR the low 3 bits of the row number": the 8
rows of the same logical column `c` land in 8 different chunk slots. The swizzle only permutes **chunk
positions** and does not scatter the 8 elements inside a chunk, so `ldmatrix` (both members) and the 16 B
copies of `cp.async` are unaffected — their atomic unit is exactly one chunk. When K exceeds 64 elements, one
box only holds 64 columns, and the face = several boxes side by side along K, each box 8 KiB (for M = 64)
with a 128 B row pitch; **all of this is generated by `tile_to_shape`, and views are derived by
`composition` — do not compute boxes and XOR by hand** (gotchas 1, 2).

## Minimal runnable example

Every snippet has actually been run by the GPU-certification probe (the probe is not included in
this release; M = 64, K = 128, bf16, 4 warps, write side
`cp.async` 16 B/thread, read side `LDSM.x4` / `LDSM.x2`, `mma.sync m16n8k16`; verdicts in §Sources).

### 1) Host side (inside the `@cute.jit` body): the face + three views, all derived from one `tile_to_shape`

```python
import cutlass
import cutlass.cute as cute
from cutlass.cute.nvgpu import cpasync, warp, warpgroup

BF16, F32 = cutlass.BFloat16, cutlass.Float32
M, K, BOX = 64, 128, 64            # BOX = columns of one K_SW128 box (64 × 16-bit = 128 B)
NBOX = K // BOX

atom = warpgroup.make_smem_layout_atom(warpgroup.SmemLayoutAtomKind.K_SW128, BF16)
face = cute.tile_to_shape(atom, (M, K), order=(0, 1))      # (M, K) logical face: NBOX (M, 64) boxes
#                                                            order=(0,1): fill one box along M first, then move to the next box

# The right operand of composition is written in the face's colex coordinate space: index = r + M*c
# ("rows step 1, columns step M" — not memory strides! see gotcha 1)
w3 = cute.composition(face, cute.make_layout((M, BOX, NBOX), stride=(1, M, M * BOX)))   # write view (r, c%64, box)
a4 = cute.composition(face, cute.make_layout((16, 16, M // 16, K // 16),
                                             stride=(1, M, 16, 16 * M)))                # A sub-block view
b3 = cute.composition(face, cute.make_layout((M, 16, K // 16), stride=(1, M, 16 * M)))  # B sub-block view
```

The four modes of `a4` are `(row within sub-block, k within sub-block, row-block index, k-block index)`;
slicing `[(None, None, wid, kb)]` gives one warp's `(16, 16)` A operand on the `kb`-th k-block; slicing `b3`
with `[(None, None, kb)]` gives the `(M, 16)` B operand (N automatically issues several beats along the rest
mode). **They cover the same logical coordinates as a direct view like
`make_layout((16,16,4,8), stride=(K,1,16*K,16))` on a flat face**, so the read-side code does not change.

### 2) Kernel side: several views from the same `MemRange`; split a `ComposedLayout` into `.outer` + `swizzle=.inner`

```python
@cute.struct
class SS:
    a: cute.struct.Align[cute.struct.MemRange[BF16, M * K], 1024]   # 1024 B alignment: the swizzle period
    b: cute.struct.Align[cute.struct.MemRange[BF16, M * K], 1024]

st  = cutlass.utils.SmemAllocator().allocate(SS)
sA3 = st.a.get_tensor(w3.outer, swizzle=w3.inner)     # write view
sA4 = st.a.get_tensor(a4.outer, swizzle=a4.inner)     # read view, the same bytes
sB3 = st.b.get_tensor(w3.outer, swizzle=w3.inner)
sB4 = st.b.get_tensor(b3.outer, swizzle=b3.inner)
```

**Every** way of reading the same piece of smem is "one more `get_tensor`"; the swizzle hangs on the
pointer, and every view and every slice (including the dynamic coordinate `wid`) applies it when computing
addresses.

### 3) Write side: `cp.async` 16 B/thread, **groups of 8 lanes write one 128 B row within a box**

```python
cp_atom  = cute.make_copy_atom(cpasync.CopyG2SOp(cache_mode=cpasync.LoadCacheMode.GLOBAL),
                               BF16, num_bits_per_copy=128)
cp_tiled = cute.make_tiled_copy_tv(cp_atom, cute.make_layout(8), cute.make_layout(8))  # 8 lanes × 8 elements
thr_cp   = cp_tiled.get_slice(tidx % 8)
team     = tidx // 8                                   # 128 threads -> 16 groups
# gA3: global-side view of the same shape (M, NBOX, BOX) (on torch, .view(M, NBOX, BOX) is enough)
for i in cutlass.range_constexpr(M // 16):
    r = i * 16 + team
    for box in cutlass.range_constexpr(NBOX):
        cute.copy(cp_tiled, thr_cp.partition_S(gA3[(r, box, None)]),
                  thr_cp.partition_D(sA3[(r, None, box)]))   # partition_D consumes the swizzled view directly
cp_async_commit_group()          # inline PTX, see the cp_async entry §3
cp_async_wait_group(0)
cute.arch.fence_view_async_shared()
cute.arch.sync_threads()
```

One warp = 4 groups = 4 rows × 128 B within one box: the 8 chunks of each row still cover all 32 banks after
the XOR, and 4 wavefronts is the lower bound for these 512 B — the write side is conflict-free too (probe
R1's `max_diff=0` proves the landing positions are right; the write-side wavefront count belongs to the
acceptance scope of [`cp_async`](cp_async.md)).

### 4) Read side: the `ldmatrix` trio fetches operands per k-block (the same code as for a flat face)

```python
mma = cute.make_tiled_mma(warp.MmaF16BF16Op(BF16, F32, (16, 8, 16)), (1, 1, 1))
tcA = cute.make_tiled_copy_A(cute.make_copy_atom(warp.LdMatrix8x8x16bOp(False, 4), BF16), mma)
tcB = cute.make_tiled_copy_B(cute.make_copy_atom(warp.LdMatrix8x8x16bOp(False, 2), BF16), mma)

lane, wid = cute.arch.lane_idx(), cute.arch.warp_idx()
thr, thrA, thrB = mma.get_slice(lane), tcA.get_slice(lane), tcB.get_slice(lane)
acc = cute.make_rmem_tensor(thr.partition_shape_C((16, M)), F32)
acc.fill(0.0)
for kb in cutlass.range_constexpr(K // 16):
    a_blk = sA4[(None, None, wid, kb)]                 # (16, 16), dynamic warp coordinate
    b_blk = sB4[(None, None, kb)]                      # (M, 16)
    frA = thr.make_fragment_A(thr.partition_A(a_blk))
    frB = thr.make_fragment_B(thr.partition_B(b_blk))
    cute.copy(tcA, thrA.partition_S(a_blk), thrA.retile(frA))   # LDSM.16.M88.4, 4 phases of 8 rows × 16 B each
    cute.copy(tcB, thrB.partition_S(b_blk), thrB.retile(frB))   # LDSM.16.M88.2 × (M/8)
    cute.gemm(mma, acc, frA, frB, acc)
```

The 8 row addresses of each phase: the same logical chunk column, 8 consecutive rows → 8 different chunk
slots after the XOR → 1 wavefront.

### 5) Acceptance: conflicts must be **measured**; the values won't show them

```
ncu --metrics l1tex__data_bank_conflicts_pipe_lsu_mem_shared_op_ld.sum,\
              l1tex__data_pipe_lsu_wavefronts_mem_shared_op_ld.sum  -k regex:<kernel> ...
```

Flat face vs swizzle face in the same kernel: the swizzle face's `bankconf_ld` ≤ 1/8 of the flat face's
(probe R3's criterion; theoretical value 0 vs 7 replays per phase). PTX census: `cp.async.cg.shared.global`
present, `ldmatrix` without `.trans` (both operand faces are K-contiguous, so the non-transposed member is
taken).

## Gotchas

1. **The right operand of `composition` is written in the face's coordinate space, not as memory strides.**
   The `make_layout((16,16,4,8), stride=(K,1,16*K,16))` customary on a flat face uses **memory element
   strides**; used directly as the right operand of `composition`, it yields a scrambled view that treats
   `r*K + c` as a colex index and decodes it — legal shape, compiles, wrong values. The spelling is "rows
   step 1, columns step M": `(16,16,M//16,K//16) : (1, M, 16, 16*M)`. Self-check: every stride of the right
   operand should be `1` or a multiple of it (row direction) / a multiple of `M` (column direction).
   (Certified: R2 uses this set of strides, `max_diff=0`.)
2. **Don't compute boxes and XOR by hand.** `tile_to_shape(atom, (M, K), order=(0,1))` already encodes into
   the layout both "the kb-th 16-column k-block lands in box kb//4" and the chunk permutation; views are
   always derived by `composition`, and a mode that crosses boxes (e.g. `b3`'s k-block mode, whose stride
   `16*M` crosses a box's `64*M`) is split by the layout algebra itself into `(within box, across boxes)`.
   A hand-written `dl ^ ((dl >> 3) & 0x70)` is only needed on the path that takes addresses directly in
   inline PTX ([`cp_async_predicated_zfill`](cp_async_predicated_zfill.md) gotcha 8).
3. **Padding is another solution to the same problem, at the cost of smem.** Changing the row pitch to an
   **odd multiple** of 16 B (K = 64 → 72, K = 128 → 136) also makes the chunk numbers of 8 rows distinct
   mod 8, with no swizzle at all on either side; the cost is 12.5% / 6.25% more face, and the row pitch is no
   longer a power of two — the 16 B destination alignment of `cp.async` still holds (16 × odd). Use this
   entry when it doesn't fit in a fixed smem budget; use padding when it fits and you want one concept
   fewer. The two routes are mutually exclusive; don't stack them.
4. **The conflict analysis is the same for both `ldmatrix` members.** The transposed member
   (`transpose=True`) likewise has 8 lanes per phase each give one row address and fetch 16 B; only the
   distribution of elements in registers differs; so the face's row pitch decides whether there are
   conflicts, independent of the member. The member is still decided by "which mode of the face is
   contiguous" (the invariant of [`ldmatrix_stmatrix`](ldmatrix_stmatrix.md)), and the swizzle does not
   change the contiguous mode.
5. **A `ComposedLayout` cannot be passed whole to `get_tensor(layout, swizzle=...)`**: it raises
   `TypeError("incompatible layout with swizzle")`; always use `.outer` + `swizzle=.inner` (same as
   [`wgmma_mn_major_operand`](wgmma_mn_major_operand.md) gotcha 5). The flat control face has no `.outer`;
   when both faces share one kernel, use a small **undecorated** helper that picks the branch by a Python
   boolean (the probe's `_view`).
6. **The swizzle period is 1024 B; the `MemRange` must be 1024 B-aligned.** Without `Align[..., 1024]`, the
   XOR uses the wrong low 3 bits of the row number — the values don't match, and the whole block is wrong.
7. **Groups of 8 lanes writing one row within a box is the certified write-side spelling.** Groups of 16
   lanes writing a whole 256 B logical row at once (`partition_D(sA[(r, None)])`, a slice spanning two boxes)
   was only observed through the fact channel in the probe, not as a contract; before using it, check the
   conclusion of the `FACT F` line in the probe log.
8. **Conflict counts are invisible to correctness; acceptance must use NCU or a control kernel.** An 8-way
   conflicting face gives all-correct values; the control of §5 (two faces in the same kernel) is the
   cheapest machine-read criterion. Hang a line such as `bankconf_ld ≤ 1.5 × healthy line` in the gate, not
   just checks on kernel count and block size.
9. **`order=(0,1)` and `(1,0)` are not the same bytes.** `(0,1)` fills one (M, 64) box along M first, then
   moves to the next box (this entry); `(1,0)` lays boxes along K first, then moves to the next row block —
   the box numbering order differs. Both are correct when views are derived by `composition`, but TMA / other
   box views must be built with the same order; mixing them is the hand-computation error of gotcha 2.
10. **The 8×8 tile face ([`ldmatrix_stmatrix`](ldmatrix_stmatrix.md) gotcha 8) is another read-side
    conflict-free face, but the 16 B chunks of one row are 128 B apart in it.** When `cp.async` writes 16
    B/thread by row, the chunks of the same row all land in the same bank group — the wavefronts saved on the
    read side are paid back on the write side (an analytic conclusion; this entry did not count it). For an
    operand face fed row by row by `cp.async`, use this entry's swizzle face.

## Acceptance lines (machine-checkable)

- NCU: the kernel's `l1tex__data_bank_conflicts_pipe_lsu_mem_shared_op_ld.sum` ≤ 1/8 of the flat control
  (theoretically 0); `smem_wavefronts_ld` back to "4 per `LDSM.x4`, 2 per `LDSM.x2`".
- PTX census: `ldmatrix` present and without `.trans`; `cp.async.cg.shared.global` present.
- smem footprint: **byte-identical** to the flat face (`cute.cosize(face) == M * K`).

## Out of scope for this entry

- MN-contiguous operand faces (the `MN_SW*` atom family): same swizzle, transposed base layout, see
  [`stsm_transpose_exchange`](stsm_transpose_exchange.md);
- WGMMA descriptors reading a swizzle face ([`wgmma_ss_min_gemm`](wgmma_ss_min_gemm.md)) — there the
  hardware undoes the swizzle; this entry is `ldmatrix` through the generic proxy;
- volume-type smem failures (wavefronts over the line while bankconf is clean):
  [`smem_traffic_triage`](smem_traffic_triage.md).

## Landing (production readings)

The complete chain on one run: H100 locked at 1590 MHz, same-job paired device window,
`vs_ref_device` = reference ÷ student.

| Step | Reading | job |
|---|---|---|
| Trigger: M0 first green; p1's q/k are flat `(64, 128)` bf16 row-major faces (row pitch 256 B = integer multiple of 128 B → 8-way conflicts) | 0.4719 ms, 0.4917x | eval |
| Pricing: the M0 audit priced four levers on the best tree in the same job (base / +each / all / all−each × 3 rounds) | `p1_pad` **add +53.18% / remove −36.04%, independent**; the other three levers +0.59% ~ +2.16% or noop | lever-price |
| Diagnosis | `G3 @ KB:ldmatrix_wideK_conflict_free_face` | — |
| Certification | this entry's R1/R2/R3/C1 all PASS, `bankconf_ld` 286720 → 0 | GPU probe |
| **Landing**: reopen D0.12 (the p1 architecture row) and switch the face per this entry | **0.4719 → 0.30229 ms (−35.9%), 0.4917x → 0.7625x** | eval (re-measured: 0.30224 ms / 0.7633x) |
| The tree that met the target still uses it | the run stopped at the target at 1.0946x (median of three jobs) | — |

How to read it — keep three things separate:

- **What was priced is the padding form** (`p1_pad`), not this entry's swizzle form. Both remove the same
  conflicts; this entry is the one with zero extra smem; the pricing says "what the conflicts are worth", the
  landing says "this entry's form cashed it in".
- **−35.9% is the reading of the whole D0.12 row, not this entry's share alone.** D0.12 was a reopen of the
  whole "p1 architecture" row; the face switch landed together with it and was not ablated on its own on the
  landed tree. It being almost equal to the pricing's remove −36.04% says the face switch is the dominant
  component of that row, but this is an inference, not an isolated measurement.
- **The kernel.py of the tree that met the target still builds the face per this entry** (`K_SW128` in 6
  places, `make_smem_layout_atom` in 3, 2 each on the M0 tree), so it is not a one-off gain that was replaced
  midway.
