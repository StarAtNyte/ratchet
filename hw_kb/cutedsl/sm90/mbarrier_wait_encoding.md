# mbarrier_wait_encoding (two encodings of an mbarrier wait: suspending wait ↔ non-blocking try/test + explicit spin)

> One file per hardware interface. Operator-agnostic; mechanism only.
>
> This entry governs only **how the wait is encoded**, not how the pipeline is built. Setting up the ring /
> arrive count / phase is in [`wgmma_tma_mbarrier`](wgmma_tma_mbarrier.md) and
> [`pipeline_runtime_subring`](pipeline_runtime_subring.md); "should it be an mbarrier rather than an
> all-party rendezvous" is in [`handoff_sync_choice`](handoff_sync_choice.md). The three are orthogonal: with
> the right primitive and the right pipeline, the wait encoding can still be the wrong tier.

## Purpose

For the same mbarrier and the same phase, CuTe DSL offers **two wait encodings**. Their synchronisation
semantics are identical (both acquire, both recognise the same phase parity); they differ only in **what the
warp does while the wait is not yet satisfied**:

- **Suspending**: the hardware puts the warp to sleep and wakes it when the barrier flips;
- **Non-blocking + explicit spin**: returns a `Boolean`; the warp stays resident and retries itself.

When the wait is on the critical path, the wake-up latency of "go to sleep, then get woken" is charged to the
total time **per wait**, and it is invisible in every throughput-type metric (tensor / dram / bytes) — it only
shows up in the stall ledger as the sleep family.

## When needed (trigger)

- **The sleep family has a significant share of the stall ledger**, and the lines hit by SASS
  `NANOSLEEP.SYNCS`, traced back, are exactly the call sites of `producer_acquire` / `consumer_wait` (the
  stall reason on these lines is usually dominated by `long_scoreboard` — the warp hangs on an asynchronous
  completion).
- On the structural side, all of these hold: the mbarrier pipeline is **already built** (not the rendezvous
  form), the wait targets are right (waiting on the beat it should wait on), and the tensor metrics match the
  structure — i.e. **nothing explains it except the wait points themselves**. This is the differential between
  this entry and two look-alike symptoms:
  - wrong supply issue organisation → `stall_long_sb` high **and** tensor low **and** fetches interleaved one by
    one with address arithmetic (see [`gather_index_prefetch`](gather_index_prefetch.md));
  - wrong primitive → dense `BAR.SYNC` with `PHASECHK`/`DEPBAR` absent (see
    [`handoff_sync_choice`](handoff_sync_choice.md)).
- **Counter-trigger (read before acting)**: when the wait rarely actually happens (the producer leads by
  enough, the stages are deep enough), the two encodings show no measurable difference; and spinning takes
  issue slots, with one smem barrier read per retry, so with many concurrent warps on the SM it can be
  **slower**. This is a lever that requires a same-job A/B, not a default.

## Mechanism: two API surfaces over the same barrier

| | Suspending (default) | Non-blocking + explicit spin |
|---|---|---|
| pipeline entry | `pipeline.consumer_wait(state)`<br>`pipeline.producer_acquire(state)` | `pipeline.consumer_try_wait(state)`<br>`pipeline.producer_try_acquire(state)` |
| sync-object entry | `MbarrierArray.wait(index, phase)` | `MbarrierArray.try_wait(index, phase)` |
| arch entry | `cute.arch.mbarrier_wait(bar, phase)` | `cute.arch.mbarrier_try_wait(bar, phase)`<br>`cute.arch.mbarrier_test_wait(bar, phase)` |
| return value | `None` (loops internally until satisfied) | `Boolean` token (the result of **one** attempt) |
| lowering | goes to the **try-wait** family (`mbarrier.try_wait*`), carrying a hard-coded suspendTimeHint; the retry loop is **generated by the compiler** | goes to `mbarrier.try_wait*` / `mbarrier.test_wait*`, **without a hint**; the loop is **written by you** |
| when not satisfied | suspends the warp (`NANOSLEEP` appears in SASS) | returns `false`; the warp stays resident |

`cute.arch.mbarrier_wait` hard-codes the suspendTimeHint as `10_000_000` (10 ms). That is an **upper bound on
the suspension time**, not the wait time — the hardware wakes the warp when the barrier flips. The point is
not this value but that this path encodes "waiting" as **sleep–wake**: every wait pays one wake-up latency.
The non-blocking surface has no such segment.

Whether the hint appears as the 4th operand in the final PTX or is absorbed by the backend into the retry
loop it generates is an implementation choice of NVVM; **don't use the operand count as the criterion**. There
are two stable, dependable layers to tell them apart: at the **PTX layer** the two paths land in **mutually
exclusive instruction families** (the blocking surface emits only `mbarrier.try_wait*`, `mbarrier_test_wait`
emits only `mbarrier.test_wait*`); at the **SASS layer** only the blocking surface leaves the `NANOSLEEP`
suspension footprint. The certification probe prints the measured census of both layers line by line; read it
from there.

The difference between `mbarrier_test_wait` and `mbarrier_try_wait` is **whether the hardware is allowed to
suspend briefly**: `test_wait` is a pure query (never suspends), `try_wait` allows the implementation to
suspend for an implementation-defined short time. Both return a `Boolean`, both carry acquire semantics, and
both need you to write the retry loop yourself.

## Minimal runnable example

Three snippets, from least to most invasive. `pipe` is any `cutlass.pipeline.PipelineAsync` subclass
(including `PipelineTmaAsync`); `cstate` / `pstate` are states built by `make_pipeline_state`.

### (a) A zero-change probe first: token form

Natively supported by the DSL: make **one** non-blocking attempt first, and fall back to the suspending wait
only on failure. The common already-ready case pays no suspension at all. Smallest change; try this first.

```python
tok = pipe.consumer_try_wait(cstate)
pipe.consumer_wait(cstate, tok)     # token true -> the internal if_generate skips the blocking wait
```

### (b) Tight spin on the consumer side (replace suspension entirely)

`consumer_wait` does nothing but wait, so once the spin is satisfied it can be **dropped entirely**.

```python
tok = pipe.consumer_try_wait(cstate)
while tok == 0:                      # dynamic Boolean -> scf.while; see gotcha 5
    tok = pipe.consumer_try_wait(cstate)
# here the full barrier is ready; consume stage `cstate.index` directly
...
pipe.consumer_release(cstate)
cstate.advance()
```

### (c) Tight spin on the producer side (the token **must** be handed back)

`producer_acquire` does more than wait: for `PipelineTmaAsync` it is also responsible for the
`arrive_and_expect_tx` on the full barrier. So after spinning, the producer side cannot simply skip it — hand
the satisfied token back; the wait is skipped and the other actions still happen.

```python
tok = pipe.producer_try_acquire(pstate)
while tok == 0:
    tok = pipe.producer_try_acquire(pstate)
pipe.producer_acquire(pstate, tok)   # wait skipped; the expect_tx arrive still happens
# issue this stage's TMA / write this stage's smem
...
pipe.producer_commit(pstate)
pstate.advance()
```

### (d) The barest layer: spin directly on the barrier owned by the pipeline

When you need pure-query semantics (not even a brief suspension), take the barrier pointer from the pipeline
and issue `mbarrier_test_wait` yourself. **For which pointer to take, see gotcha 1.**

```python
# consumer waits on the full barrier
fbar = pipe.producer_get_barrier(cstate)          # take the index from your own state
ok = cute.arch.mbarrier_test_wait(fbar, cstate.phase)
while ok == 0:
    ok = cute.arch.mbarrier_test_wait(fbar, cstate.phase)

# producer waits on the empty barrier
ebar = pipe.consumer_get_barrier(pstate)
ok = cute.arch.mbarrier_test_wait(ebar, pstate.phase)
while ok == 0:
    ok = cute.arch.mbarrier_test_wait(ebar, pstate.phase)
```

### (e) Hand-allocated barriers: a `try_wait` spin inside a `@cute.jit` helper (drop-in replacement for `cute.arch.mbarrier_wait`)

When the barrier is not a pipeline object but a raw pointer hand-initialised with `mbarrier_init` in
`SharedStorage`, there is no `consumer_try_wait` layer; replace `cute.arch.mbarrier_wait(bar, phase)` directly
with a helper carrying its own `@cute.jit` (gotcha 5), call site by call site, arguments unchanged:

```python
@cute.jit
def bar_wait_spin(bar, phase):
    ok = cute.arch.mbarrier_try_wait(bar, phase)   # try family: allows a brief hardware suspension, no hint
    while ok == 0:
        ok = cute.arch.mbarrier_try_wait(bar, phase)

# call site: cute.arch.mbarrier_wait(bar_full, par)  ->  bar_wait_spin(bar_full, par)
```

Usable on both sides (producer waiting on empty, consumer waiting on full): a hand-made barrier has no
expect_tx hidden inside a `producer_acquire` (gotcha 2), so the producer side can be replaced entirely too;
arrive / init counts stay untouched (gotcha 8).

**(e′) An inline-PTX stand-in when the arch surface is missing** (same instruction, same semantics; when the
build does not export `cute.arch.mbarrier_try_wait`, probe once with `getattr` and choose):

```python
@dsl_user_op
def mbar_try_wait_i32(mbar_addr, phase, *, loc=None, ip=None) -> cutlass.Int32:
    # One parity attempt -> 1 satisfied / 0 not satisfied. The operand is the Int32 shared-window address
    # (Pointer.toint()), not a generic 64-bit pointer (the DSL refuses the conversion).
    return cutlass.Int32(llvm.inline_asm(
        T.i32(),
        [cutlass.Int32(mbar_addr).ir_value(loc=loc, ip=ip),
         cutlass.Int32(phase).ir_value(loc=loc, ip=ip)],
        "{\n\t.reg .pred p;\n\t"
        "mbarrier.try_wait.parity.shared::cta.b64 p, [$1], $2;\n\t"
        "selp.b32 $0, 1, 0, p;\n}",
        "=r,r,r,~{memory}",          # ~{memory} + has_side_effects: see below
        has_side_effects=True, is_align_stack=False,
        asm_dialect=llvm.AsmDialect.AD_ATT, loc=loc, ip=ip))

_arch_try_wait = getattr(cute.arch, "mbarrier_try_wait", None)
if _arch_try_wait is not None:
    @cute.jit
    def bar_wait_spin(bar, phase):
        ok = _arch_try_wait(bar, phase)
        while ok == 0:
            ok = _arch_try_wait(bar, phase)
else:
    @cute.jit
    def bar_wait_spin(bar, phase):
        addr = bar.toint()
        ok = mbar_try_wait_i32(addr, phase)
        while ok == 0:
            ok = mbar_try_wait_i32(addr, phase)
```

Both `has_side_effects=True` **and** the `~{memory}` clobber are needed: this asm has a return value, and
relying only on "it has a return value so it won't be DCE'd" is not enough — **[INFERRED]** a pure-function asm
without the clobber can be hoisted out of the `while` body, after which every trip compares the same stale
register, and the behaviour would be **spinning forever** (a hang, not a wrong result). The certified tree
passed gotcha 10's repeated-launch contract with both in place; the control variant without the clobber was
never run, so start a probe before citing "removing it hangs".

## Gotchas

1. **The name of a barrier accessor says "who signals", not "who waits".**
   `producer_get_barrier(state)` returns the **full** barrier (the one the producer arrives on), which is
   exactly what the consumer must wait on; `consumer_get_barrier(state)` returns the **empty** barrier, which is
   what the producer must wait on. Both take `index` from **the caller's own** state. Getting them backwards =
   deadlock (waiting for a phase that never flips) or early release (reading a stage not fully written).

2. **The producer side must not delete `producer_acquire` entirely.** For `PipelineTmaAsync`,
   `producer_acquire` = two things: "wait for empty" + "`arrive_and_expect_tx` on the full barrier". Spinning
   without calling it = the transaction count is never set = the full barrier is never full = deadlock. The
   correct spelling is (c)'s token hand-back; if you really want to hand-roll it, you must add
   `cute.arch.mbarrier_arrive_and_expect_tx(pipe.producer_get_barrier(pstate), tx)` yourself. The consumer
   side has no such problem (`consumer_wait` only waits).

3. **The token form leaves a dead branch in the binary.** The skip in `producer_acquire(state, tok)` is a
   **runtime** `scf.if`, not resolved at compile time: the blocking wait's code is still in SASS, so **the
   static `NANOSLEEP` count does not drop to zero**. Acceptance must use **dynamic** readings (the stall share
   of the sleep family / end-to-end time); using the static count as the criterion leads to the false
   conclusion "the switch didn't take". Only dropping `consumer_wait` entirely as in (b) brings the consumer
   side to a static zero.

4. **Use the caller's own `state.phase` for the phase; don't make your own.**
   The initial phase of `make_pipeline_state(PipelineUserType.Producer, stages)` is **1** (the first round
   treats empty as already empty), and Consumer's is **0**; `state.advance()` flips the phase only when the
   index wraps to 0. When hand-writing a spin, just copy `state.phase`; keeping your own phase copy is the main
   source of off-by-one errors, and a wrong phase shows up as a deadlock or reading a stale stage, not an error.

5. **`while tok == 0:` must sit in a scope the preprocessor can enter.** That is, inside the body of a
   `@cute.kernel` function, or inside a helper **carrying its own `@cute.jit`**. Written into an undecorated
   plain helper, the dynamic `Boolean` is evaluated as a Python bool at trace time →
   `PHASE_DYNAMIC_TO_STATIC_BOOL`. See [`cute_dsl_trace_scope`](cute_dsl_trace_scope.md).

6. **Spinning is not free; a same-job A/B is mandatory.** Spinning takes issue slots, with one smem barrier read
   per retry. When waits are sparse (deep stages, the producer far ahead) or there are many concurrent warps on
   the SM, the execution resources the suspending wait gives up are worth more than the wake-up latency saved.
   This entry is a **lever**, not a **default**: changing the encoding needs a same-job before/after
   comparison, not a decision from the symptom alone.

7. **`mbarrier_conditional_try_wait(cond, bar, phase)` is not a spin primitive.** It means "try once only if
   `cond` is true, otherwise return `True` directly", for putting one attempt under a predicate; using it as a
   loop body "succeeds" and releases immediately when `cond` is false. To spin, use `mbarrier_try_wait` /
   `mbarrier_test_wait` with an explicit `while`.

8. **Don't change the arrives along the way.** This entry only touches the **waiting** side. Changing the
   counts or issuing-thread counts of arrive / release / expect_tx is a deadlock or a silent error, and is
   completely orthogonal to the wait encoding.

9. **A spin encoding rewrites the dossier's mbarrier census readings; the structure did not change.** For the
   same set of fixed-address hand-made barriers with no stage-index arithmetic, switching only the waits from
   suspending to (e)'s spin, the NCU dossier census read: `spin_loops` 14 → 27; mbarrier objects UNRESOLVED
   5 → 0, tiers `{CONST: 12}` → `{CONST: 10, RING: 10}`; contract axis `rings` `[]` → 10 × `stride=0xe000`; the
   set of inter-role edges was rewritten along with it. There is no ring at all in the source (every barrier is
   one fixed object in `SharedStorage`); what happened is that the address chain the compiler generated for the
   explicit retry loop was read by static chain-following as "initial value + increment stride". Reading: when
   `rings` / `mbar_tiers` flip after a wait-encoding change, check the source first — do the barriers have
   stage-index arithmetic? If not, record it as a codegen follow-on effect, neither as the prime suspect nor as
   evidence that "a ring has been built". Which axes flip is **a property of the tree**, not of the encoding: on
   a tree whose slot indices are compile-time constants and whose barrier addresses are fixed offsets, the same
   switch to (e) left `rings` / `mbar_tiers` completely unmoved, and what flipped was `loops` and the per-region
   `commit` / `supply` — the hand-written `while` loops were that tree's first back edges
   ([`ptx_sass_census_criteria`](ptx_sass_census_criteria.md) gotcha 11). The two cases have only one thing in
   common: what a wait-encoding change leaves on the dossier is **back edges**, not new synchronisation objects.

10. **The correctness contract for changing the wait encoding is not one launch but "repeated launches on the
    same input + bit-exact comparison".** Of the three failures of a wrongly written spin — wrong phase, the
    attempt hoisted out of the loop, a lost acquire letting the consumer read a half-written slot — the first two
    are hangs and the third is a **data race**: a single launch can pass by luck. Write the contract as the same
    input launched N times back to back in one process (N=12 is enough), each one passing the criterion, and
    **outputs that are deterministic by construction being bit-identical** (quantities accumulated in a fixed
    order within each CTA; outputs of unordered cross-CTA reductions are not bound by this and only report
    drift). The control variant in the same job uses the suspending wait; when the control variant dies together
    with the experimental one, suspect the probe's replication scaffolding before the encoding
    ([`gpu_probe_ladder`](gpu_probe_ladder.md) gotcha 4).

11. **Readings of the `stride=0x1` family on the `rings` axis (bare `stride=0x1` / `slots=253` / `slots=9` /
    `wrap=sel`) are codegen fingerprints of the phase / index arithmetic chain; they do not encode ring
    depth.** The census reads an AND mask on the barrier address chain as `slots = (mask + 1) / stride` and a
    SEL as `wrap=sel` (the definition in the tool `orch_tools.resolve_addr`): on a stride-1 chain, `slots=253`
    is just mask 0xfc and `slots=9` is mask 0x8 — neither is the depth of any ring. Readings of four KEEPs on
    the same tree:
    - a rewrite of a whole stretch of the middle role (zero mbarrier source changes, all ring depths
      unchanged): `[slots=9, wrap=sel]` → `[slots=253, slots=9, wrap=sel]`;
    - two wgmma chains merged into one commit group (rings unchanged): the `slots=253` one → bare `stride=0x1`;
    - **actually changing depth** (two rings 2 → 3, two rings 5 → 3): bare → `slots=253` — the **same** reading
      as the first item, and no `slots=3` appeared;
    - deleting the exit segment of a handoff surface + switching one chain to fp16 operands (ring depths
      unchanged, one empty count 128 → 384): `[bare, slots=9, wrap=sel]` → `[bare, slots=253, slots=9, wrap=sel]`.
    Seven later KEEPs on the same tree nail down "the flips are unrelated to wait points" even harder (each
    reading comes from that KEEP's own eval job):
    - moving one SS wgmma chain together with its elementwise slot exit from role A to role B (A loses two
      mbarrier wait points, B gains one; ring depths and arrive counts unchanged):
      `[bare, slots=253, slots=9, wrap=sel]` → `[bare, slots=9]`, with `slots=253` and `wrap=sel` disappearing
      **together**; the same move with the new fragment borrowing the registers of a dead fragment (spill
      7,022,592 → 0, instruction order unchanged) left the reading **unchanged**; moving it back brought the four
      back as they were.
    - a **purely register-side** rewrite within one role, zero mbarrier source changes: narrowing the slot exit
      to delete the f32 staging fragment → the four reduce to `[slots=9]`; then keeping 32 f32 factors resident
      across one chain → `[slots=9, wrap=sel]`; these three landed as one bundle read **the same** as "the third
      landed alone" (both `[slots=9, wrap=sel]`).
    - **code AST unchanged, only the two `setmaxnreg` tier constants changed** (104/192 → 120/184):
      `[slots=9, wrap=sel]` → `[bare, slots=9]`.
    - adding only one 128-thread named-barrier rendezvous (zero mbarrier changes): the reading is the same as
      the baseline's four.
    Reading: flips in the count and membership of this family are always recorded as codegen follow-on effects
    — it changes even with the **register tiers** — neither as the prime suspect, nor as proof that "the depth
    got into the cubin" or "the addition/removal of wait points got into the cubin". The footprint of a depth
    change is in the dynamic smem byte count and the barrier object count; for how to read it see
    [`ring_depth_lever`](ring_depth_lever.md).

12. **The third KEEP of form (e): two readings on the same tree, whose sign depends on whether the suspending
    wait is still on the hot path — not on the `stall_barrier` share.** The knob: change only the two full wait
    points inside the dynamic loop body (one at the loop top, one after it) from suspending to (e), keeping the
    other ten off-chain wait points as `cute.arch.mbarrier_wait`, with the variant chosen by a `cutlass.const_expr`
    constant (the suspending variant is compiled away rather than skipped by a branch). Footprint: loop-body
    `NANOSLEEP` 0, 6–8 try-wait instructions, whole-kernel `NANOSLEEP` still 10 (the ten off-chain ones);
    dossier `rings` `["stride=0x1"]` → `["stride=0x1", "stride=0x1ff,wrap=sel"]` (another back-edge follow-on,
    gotcha 9).
    - **Reading A (in-process pairing, on the tree before landing)**: both wait points take the suspending wait
      every trip, and the data has always already arrived (pure PHASECHK round trips), `stall_barrier` 1.33%,
      `tensor_pct` 76.3. With mirrored interleaved timing in one process, the e2e median ratio control / (e) was
      **1.0184** (a variant issuing the two try-waits back to back merged into one spin: 1.0187); the three
      variants' outputs were bit-identical, spread 0.3%. That probe's own criterion line is 1.02, so the
      contract is recorded as FAIL against the line — direction stable, magnitude below the line; the ablation
      "remove both wait points" gives an upper bound of +7.48% (NCU clock).
    - **Reading B (on the tree at KEEP landing)**: between A and the landing there was one change — the
      `mbarrier_try_wait` of both wait points is issued one round early (squeezed into the middle of the previous
      elementwise stream), the predicate is carried across the back edge to the loop top, and only an
      `if p == 0:` miss falls through to the blocking wait. On this tree, switching the miss path to (e) as well:
      the same-job ratio given by an unchanged control kernel run alongside in each eval job differed by only
      +0.07% before and after (flat), `stall_barrier` 1.27 → 1.25. The gate window 0.21719 → 0.2183 ms is
      **absolute milliseconds across jobs**, and the unchanged control kernel itself drifted +0.6% between the
      two jobs, so it cannot be read as a +0.51% regression.
    - **Reading**: on a tree with 1.3% `stall_barrier`, (e) has read about +1.8% (A), so "small `stall_barrier`
      share ⇒ nothing to buy" **does not hold** — the suspending wait's tax is one wake-up latency per wait, paid
      even when the data has already arrived, and `stall_barrier` barely sees it. A consistent explanation of B
      reading flat is that the early polling had already moved the blocking wait off the hot path, leaving (e)
      only the miss path to change `[INFERRED]` — no 2×2 of "early polling × wait encoding" has been run on the
      same tree between A and B. When prioritising, the question to ask is **whether each trip of the serial
      chain still really reaches a suspending wait** (the loop-body `NANOSLEEP` count in SASS + whether a
      predicate has already been brought back before that wait point), not `stall_barrier`.
    - **Uncertified gap**: on the same tree, a variant rewriting **all 12 wait points** (including the tile
      prologue / epilogue and the producer side) into try-wait retry spins in one go failed to compile
      (`TYPE_UNSTABLE_JOIN`), with no readings; whether the failure is a problem of the rewriting method or a
      recipe gap of (e) at some class of sites was not isolated. What this entry certifies is still only the two
      loop-body sites.
